# Гибридный runtime PIOS

Этот документ описывает **один переносимый runtime-набор**, а не три параллельно исполняющие одни и те же работы системы. API, web, PostgreSQL и worker используют одну модель состояния. В каждый момент времени для конкретной базы должен быть только один активный worker leader; запуск нескольких экземпляров до добавления атомарного claim/leader election запрещён.

> Текущий worker выполняет только безопасный recovery loop. Он блокирует просроченные `running` jobs в `blocked_recovery` и **не** запускает queued jobs, LLM, browser, Telegram или другие внешние действия.

| Профиль | Назначение | Когда использовать | Что не делать |
| --- | --- | --- | --- |
| Управляемый постоянный runtime | Основной 24/7 production-контур с мониторингом и секретами на сервере. | После отдельного решения о публикации и настройки домена/секретов. | Не включать вторую копию worker против той же БД. |
| Локальный компьютер | Разработка, приватные эксперименты, резервное восстановление. | Когда компьютер владельца включён и доступен. | Не считать его круглосуточным, если устройство может выключиться. |
| Собственный сервер | Полный инфраструктурный контроль, домен, firewall и резервные копии. | Когда есть администрируемый сервер и понятная политика обновлений. | Не открывать PostgreSQL или API в интернет напрямую. |

## Portable Compose profile

`docker/docker-compose.runtime.yml` создаёт non-root containers для PostgreSQL, API, worker и web. PostgreSQL не публикуется наружу; API и web по умолчанию привязываются к loopback. Миграции — отдельная одноразовая операция, а не скрытая часть старта приложения.

Перед первым запуском создаётся отдельный production `.env` вне git. Минимально требуются `POSTGRES_PASSWORD`, `OWNER_ID`, `WEB_ORIGIN`, `API_AUTH_TOKEN`, `PIOS_API_TOKEN`, `PIOS_WEB_USERNAME`, `PIOS_WEB_PASSWORD`. API и web tokens должны быть одним и тем же случайным значением; LLM-переменные опциональны и остаются server-side.

```bash
# 1. Запустить PostgreSQL и применить миграции только после проверки резервной копии.
docker compose -f docker/docker-compose.runtime.yml --profile operations run --rm migrate

# 2. Запустить основной набор.
docker compose -f docker/docker-compose.runtime.yml up -d --build

# 3. Проверить health локально на хосте.
curl --fail http://127.0.0.1:3001/health/ready
curl --fail http://127.0.0.1:3002/health/ready
```

## Операционные safeguards

Перед реальным 24/7 запуском владелец должен определить, где хранятся резервные копии PostgreSQL, кто получает критические алерты, как ротируются secrets и каким способом выполняется rollback container image. Эти шаги намеренно не автоматизированы в репозитории: автоматизация без выбранного хоста, домена, хранилища backup и владельца secrets создала бы ложное ощущение готовности.

Ни Docker-профиль, ни этот документ не дают права на browser automation, Telegram delivery, внешние write actions или обход CAPTCHA. Такие действия появятся только за approval-gated policy boundary в следующей стадии.
