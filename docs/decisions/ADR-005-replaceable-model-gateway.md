# ADR-005: Model Gateway как заменяемый слой

- Статус: Принято
- Дата: 2026-08-05

## Контекст

Система не должна критически зависеть от одной модели или одного
провайдера (принцип 17 ТЗ / раздел 8). Разные роли (Researcher, Verifier,
Critic, генерация кода, дешёвая классификация) требуют разных моделей по
качеству и стоимости, и это должно настраиваться, а не быть зашито в код
оркестратора.

## Решение

Создаётся `packages/model-gateway`, реализующий доменные порты
`ModelProvider` и `ModelRouter`. Оркестратор и use cases никогда не
запрашивают конкретное имя модели — только `CapabilityProfile`
(`reasoning_high`, `reasoning_standard`, `coding_high`, `coding_fast`,
`vision_browser`, `research_long_context`, `verification_strict`,
`classification_cheap`, `summarization_fast`). `ModelRouter` превращает
capability в конкретного провайдера и модель через конфигурацию (файл/env),
а не через код. Первая версия включает один реальный provider adapter и
`FakeModelProvider` для тестов; архитектура должна позволять добавить
второго провайдера без изменения `orchestrator-core`. Все ответы модели,
влияющие на состояние, обязаны проходить Zod-валидацию, с ограниченной
попыткой repair при ошибке структуры и контролируемым отказом после
исчерпания попыток.

## Обоснование

- Прямое требование ТЗ (разделы 1.1, 8, 17, 23.11).
- Capability-based роутинг отделяет «что нужно сделать» (оркестратор) от
  «какая модель это лучше всего сделает и по какой цене» (конфигурация) —
  изменение прайсинга/качества провайдера не требует правок доменного кода.
- `FakeModelProvider` делает возможным тестирование когнитивного цикла без
  реальных вызовов API — быстрее, детерминированнее, бесплатно.

## Альтернативы

- **Прямой вызов SDK провайдера из use case** — отклонено: жёстко
  привязывает бизнес-логику к конкретному провайдеру, нарушает принцип
  1.1 и делает недостижимым критерий «заменить OpenAI на Anthropic без
  изменения orchestrator-core».
- **Готовый роутер (напр. LiteLLM или аналог) как прямая зависимость
  домена** — отклонено на этом этапе: такой роутер — тоже внешняя
  технология, которая должна быть адаптером за `ModelProvider`, если
  вообще используется, а не заменять сам доменный интерфейс.

## Последствия

- Добавление нового провайдера — это новый класс, реализующий
  `ModelProvider`, плюс запись в конфигурации `ModelRouter`; ноль
  изменений в `packages/application` и `packages/domain`.
- Стоимость и usage должны логироваться на уровне gateway для каждой
  модели независимо от провайдера — единый формат `UsageReport`.
- Имена конкретных моделей (например, версии моделей) живут в
  конфигурации/env, не в исходном коде бизнес-логики (раздел 8 ТЗ).
