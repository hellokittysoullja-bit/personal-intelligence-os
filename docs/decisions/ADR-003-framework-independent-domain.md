# ADR-003: Domain независим от фреймворков

- Статус: Принято
- Дата: 2026-08-05

## Контекст

Оркестратор должен принадлежать проекту, а не поставщику модели или
workflow-фреймворку (принцип 1.1–1.2 ТЗ). Если доменные сущности (Mission,
Task, AgentJob...) или use cases напрямую используют типы LangGraph,
конкретного model SDK или Fastify, замена любой из этих технологий
потребует переписывания ядра — то есть система оказывается в зависимости
именно от того, от чего её требовалось изолировать.

## Решение

`packages/domain` не имеет рантайм-зависимостей от Fastify, LangGraph,
Playwright, конкретных model SDK (`openai`, `@anthropic-ai/sdk`) — только
от TypeScript и Zod (рассматриваются как язык описания контрактов, не
фреймворк выполнения). `packages/application` зависит только от
`packages/domain` и получает реализации портов (репозитории, движки,
провайдеры) через dependency injection, не импортируя infrastructure
напрямую. Вся интеграция с конкретными технологиями — в infrastructure
пакетах (`packages/database`, `packages/model-gateway`,
`packages/workflow-engine`, `packages/browser-runtime`,
`packages/tool-runtime`), которые реализуют доменные интерфейсы (порты):
`WorkflowEngine`, `ModelProvider`, `ModelRouter`, `Tool`, `EventBus`,
`MemoryStore`, `ArtifactStore`, `PolicyEngine`, `EvaluationRunner`,
`AgentRuntime`.

## Обоснование

- Прямое требование ТЗ (раздел 1.2, раздел 4.1, раздел 23.6).
- Позволяет: заменить LangGraph без изменения домена (ADR-006), заменить
  провайдера модели без изменения `orchestrator-core` (ADR-005), добавить
  новый `Tool`/`MemoryStore`/`BrowserRuntime` без изменения главного цикла
  — это входит в критерии качества фундамента (`PRODUCT_VISION.md` §5).
- Делает domain тривиально unit-тестируемым через fake-реализации портов,
  без поднятия Postgres/LangGraph/Playwright в unit-тестах.

## Альтернативы

- **Прямое использование LangGraph state/типов в domain** — отклонено:
  быстрее на старте, но напрямую противоречит принципу 1.2 ТЗ и создаёт
  vendor lock на уровне ядра.
- **"Анемичный" domain без портов, вся логика в infrastructure** —
  отклонено: размывает границу ответственности, оркестратор перестаёт
  «принадлежать проекту» в смысле принципа 1.1.

## Последствия

- Каждая новая интеграция (новый провайдер модели, новый workflow-движок,
  новый инструмент) начинается с вопроса «какой порт домена она
  реализует», а не «как её быстрее подключить».
- Требуется дисциплина на code review: PR, добавляющий импорт
  инфраструктурного пакета в `packages/domain` или `packages/application`,
  отклоняется до объяснения или исправления.
- Возможное дополнение: architecture-lint (например,
  `eslint-plugin-boundaries`), решение о его подключении — по факту первого
  нарушения или на Milestone 1/5, не как отдельный ADR заранее.
