# ADR-004: Event log как основа аудита

- Статус: Принято
- Дата: 2026-08-05

## Контекст

Система выполняет автономные действия от имени владельца, включая
изменения файлов, команды терминала и (позже) действия в браузере и
внешние вызовы. Необходимо в любой момент объяснить, что произошло, кто
(модель/агент/владелец) это решил и почему, а также иметь возможность
остановить, приостановить и продолжить миссию без потери контекста
(критерии качества фундамента, `PRODUCT_VISION.md` §5, пункты 7–9).
История чата для этого недостаточна — она не структурирована и не
гарантирует полноты (принцип 1.4 ТЗ).

## Решение

Все существенные действия системы пишут неизменяемое событие в append-only
таблицу `mission_events` (PostgreSQL). Каждое событие содержит `eventId,
eventType, timestamp, ownerId, missionId, taskId, agentJobId, traceId,
causationId, correlationId, payload, schemaVersion`. Текущее состояние
сущностей (Mission.status, Task.status и т.д.) хранится отдельно как
read-model для быстрых запросов, но именно событийный журнал — источник
истины для аудита, Debug Timeline и объяснимости. Полноценный event
sourcing (восстановление всего состояния исключительно из событий) не
реализуется в Milestone 0–9 — это осознанно отложено (раздел 6 ТЗ), чтобы
не платить за сложность, которая не нужна на этом этапе.

## Обоснование

- Явное требование ТЗ (раздел 6, принцип 1.5 «доказательство вместо
  заявления»).
- append-only + `causationId`/`correlationId` даёт трассируемость цепочки
  решений без сложности полного event sourcing.
- Разделение «журнал для аудита» / «read-model для запросов» даёт быстрые
  запросы UI, не жертвуя полнотой аудита.

## Альтернативы

- **Только журнал приложения (Pino logs) без доменной таблицы событий** —
  отклонено: логи не структурированы как доменные сущности, сложно
  строить UI-timeline и `Evidence` на их основе, нет гарантии полноты
  (легко забыть залогировать) в отличие от события, являющегося частью
  доменного контракта use case.
- **Полный event sourcing с первого дня** — отклонено: явное указание ТЗ
  не делать этого сейчас; преждевременная сложность.

## Последствия

- Каждый use case (`CompleteTask`, `RequestApproval` и т.д.) обязан внутри
  своей транзакции одновременно обновить read-model и записать событие —
  это часть контракта use case, а не опциональный побочный эффект.
- Realtime UI подписывается на новые события (через `EventBus`), а не
  поллит состояние — упрощает `apps/web`.
- Эволюция схемы событий обязана быть обратно совместимой или явно
  версионированной через `schemaVersion` — старые события не переписываются.
