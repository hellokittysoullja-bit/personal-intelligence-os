# ADR-010: Модель согласованности состояния/событий и восстановление после сбоя

- Статус: Принято (по итогам архитектурного аудита Milestone 0)
- Дата: 2026-08-05

## Контекст

`ADR-004` фиксирует, что read-model (текущее состояние Mission/Task) и
`mission_events` обновляются в одной БД-транзакции — это защищает от
рассинхронизации состояния и журнала *в рамках одной успешной операции*.
Но архитектурный аудит Milestone 0 показал, что ни один документ не
описывал, что происходит, когда `apps/worker` падает **посреди**
операции с побочным эффектом за пределами БД-транзакции — например,
`run_command` реально выполнил команду во внешнем мире (файловая
система, потенциально в будущем — внешний API), но процесс упал до
записи `ToolCallCompleted`. Без explicit-модели восстановления возможны
два одинаково опасных failure mode при рестарте: (а) задача зависает
навечно в `running`, потому что никто не решает, что с ней делать; (б)
наивная логика слепо повторяет действие, что для неидемпотентного
действия (в будущем — например, `send_email`/`submit_form`) означает
двойное выполнение.

Это также напрямую связано с `Tool.idempotency`/`retryPolicy`
(`ARCHITECTURE.md` §5) — контракт Tool должен нести информацию,
достаточную для того, чтобы решение о безопасности повтора можно было
принять программно, а не угадывать.

## Решение

1. Статус вызова инструмента (`ToolCall`, отражается последовательностью
   событий `ToolCallStarted` → `ToolCallCompleted`/`ToolCallFailed`)
   различает как минимум три состояния при анализе после рестарта:
   *не начат* (нет `ToolCallStarted`), *начат — исход неизвестен*
   (`ToolCallStarted` есть, `ToolCallCompleted`/`ToolCallFailed` нет),
   *завершён* (есть терминальное событие).
2. При старте `apps/worker` обязателен reconciliation-проход: найти все
   Mission/Task в незавершённых статусах, чей последний `mission_events`
   старше порога живости (worker heartbeat), и для каждого такого Task
   с открытым tool call определить дальнейшее действие по
   `Tool.idempotency`:
   - `idempotent` → допустимо безопасно повторить/продолжить;
   - `not_idempotent` или `unknown` → **не** повторять автоматически;
     переводить Task в состояние, требующее решения (проверка реального
     состояния внешней системы, либо явный запрос владельцу через
     `ApprovalRequest`/уведомление) — молчаливое продолжение как ни в
     чём не бывало запрещено.
3. Graceful `pause`/`resume` (по явной команде владельца) — отдельный,
   более простой путь: `WorkflowEngine.pause()` обязан гарантировать,
   что пауза происходит на границе, где нет открытых tool call с
   неизвестным исходом (либо дождаться завершения текущего вызова, либо
   явно отменить его через `Tool` с поддержкой cancellation) — так что
   `resume()` после явной паузы не требует reconciliation-логики п.2, в
   отличие от восстановления после аварийного падения процесса.

## Обоснование

- Прямое следствие требований ТЗ: «любой бесконечный цикл — критическая
  ошибка», «все фоновые процессы поддерживают cancellation», «миссию
  можно остановить и продолжить без потери состояния» — последнее
  неявно предполагает и восстановление после сбоя, не только graceful
  pause, иначе критерий качества фундамента `PRODUCT_VISION.md` §5 п.6
  оказывается неполным.
- Явное различение трёх состояний tool call — минимальный набор,
  достаточный для безопасного решения о повторе, без необходимости
  полноценного saga-паттерна или distributed transaction на этом этапе
  масштаба (что было бы преждевременной сложностью).

## Альтернативы

- **Полагаться на естественную идемпотентность большинства read/write
  файловых операций и не формализовывать статусы** — отклонено:
  справедливо для `read_file`/`write_file` в первой версии, но
  архитектура должна быть готова к будущим tool'ам с реальными
  необратимыми внешними эффектами (раздел 12 ТЗ: «предусмотреть
  архитектурный потенциал для подключения любых будущих способностей»);
  откладывать эту модель до появления первого такого tool означало бы
  проектировать её в спешке под давлением конкретной фичи.
- **Полный event sourcing с replay для восстановления любого состояния**
  — отклонено тем же обоснованием, что и в `ADR-004`: осознанно не
  делается в Milestone 0–9 ради снижения сложности; текущее решение —
  минимальный reconciliation-проход, а не полная замена read-model на
  вывод из событий.

## Последствия

- `Tool.idempotency`/`retryPolicy`/`timeout` (`ARCHITECTURE.md` §5) —
  обязательные поля контракта, не опциональные, начиная с первой
  реализации `ToolExecutor` (Milestone 5).
- `WorkflowEngine` (Milestone 4) обязан реализовать различимую границу
  между graceful pause и recovery после сбоя — это влияет на выбор и
  настройку checkpointer'а LangGraph.js (или другой реализации).
- Reconciliation-логика на старте `apps/worker` — обязательная часть
  Milestone 4, не отложенное улучшение.
