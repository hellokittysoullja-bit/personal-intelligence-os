# ADR-007: PostgreSQL как единственный источник истины

- Статус: Принято
- Дата: 2026-08-05

## Контекст

Системе нужно надёжно хранить структурированные сущности (Mission, Task,
Event, Memory, Artifact metadata и т.д.), поддерживать транзакционную
запись состояния и событий вместе (ADR-004), полнотекстовый поиск для
памяти на раннем этапе (раздел 13 ТЗ) и архитектурный задел под векторный
поиск в будущем, не платя за него сейчас.

## Решение

PostgreSQL — единственная база данных и единственный источник истины для
первой версии. Доступ — через Drizzle ORM (`packages/database`), миграции
— через Drizzle. `pgvector` закладывается архитектурно (интерфейс
`SemanticMemoryIndex` как отдельный порт домена, см. `ARCHITECTURE.md`
§10), но не подключается, пока не появится конкретная потребность
(векторный поиск памяти, Milestone 8+). Полнотекстовый поиск памяти на
старте — стандартные средства Postgres (`tsvector`/`pg_trgm`), не
отдельная поисковая система.

## Обоснование

- Прямое требование ТЗ (раздел 3, раздел 13).
- Одна БД для всего монолита избегает распределённых транзакций и
  рассинхронизации состояния/событий (важно для ADR-004: состояние и
  событие пишутся в одной транзакции).
- Postgres поддерживает и обычные реляционные данные, и JSON(B) для
  гибких полей (`payload` события, `structuredData` памяти), и
  полнотекстовый поиск, и (через расширение) векторный поиск — закрывает
  весь горизонт Milestone 1–9 одной технологией.
- Drizzle даёт типобезопасные запросы и явные миграции без ORM-магии,
  совместимо с принципом «не использовать any без необходимости».

## Альтернативы

- **MongoDB / документная БД** — отклонено: доменная модель PIOS сильно
  реляционна (Mission→Task→AgentJob→Evidence→Artifact со множеством
  связей и статусов), транзакционная целостность важнее гибкости схемы.
- **Отдельная векторная БД (Pinecone/Weaviate) с первого дня** — отклонено:
  преждевременно, векторный поиск памяти — не требование Milestone 0–7;
  добавляется как отдельный адаптер `SemanticMemoryIndex`, когда появится
  реальная потребность (раздел 13 ТЗ, `ARCHITECTURE.md` §10).
- **SQLite для локальной простоты** — отклонено: не даёт полноценного
  `pgvector`/`tsvector` пути роста и хуже подходит для будущего
  многопроцессного доступа (api + worker к одной БД).

## Последствия

- Все репозитории (`MissionRepository`, `TaskRepository`, `EventStore` и
  т.д.) реализуются в `packages/database` поверх Drizzle и общего
  Postgres-подключения.
- Тесты интеграционного уровня требуют реальной тестовой PostgreSQL
  (Docker), что уже заложено в стек (`docker/docker-compose.yml`,
  раздел 20.2 ТЗ).
- Добавление `pgvector` в будущем — миграция + новый метод в
  `SemanticMemoryIndex`, без изменения существующих репозиториев.
