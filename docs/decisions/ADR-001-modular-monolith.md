# ADR-001: Модульный монолит вместо микросервисов

- Статус: Принято
- Дата: 2026-08-05

## Контекст

PIOS должен объединять множество способностей (миссии, модели, инструменты,
браузер, память, обучение), которые логически независимы, но на старте
имеют одного владельца, один процесс исполнения и умеренную нагрузку.
Микросервисная архитектура (в т.ч. Kubernetes) добавляет операционную
сложность (сеть, деплой, распределённые транзакции, оркестрация
инфраструктуры), которая не окупается на этом масштабе и явно исключена
требованиями (раздел 2 ТЗ: не использовать Kubernetes, не использовать
десятки микросервисов).

## Решение

Первая версия — модульный монолит: один монорепозиторий (pnpm +
Turborepo), одна PostgreSQL, один API-процесс (`apps/api`), один
worker-процесс (`apps/worker`), один web-интерфейс (`apps/web`). Внутренние
границы модулей строгие и проходят по границам pnpm-пакетов
(`packages/domain`, `packages/application`, `packages/tool-runtime` и
т.д.), а не по договорённости в коде.

## Обоснование

- Границы пакетов в монорепо дают почти те же гарантии изоляции, что и
  границы сервисов (явные зависимости в `package.json`, невозможность
  случайного импорта), но без сетевой и операционной сложности.
- Один процесс исполнения радикально упрощает отладку долгих
  многоэтапных миссий на старте проекта.
- Любой тяжёлый модуль (например, `browser-runtime` или `worker`)
  спроектирован через порт/интерфейс, поэтому может быть вынесен в
  отдельный сервис позже без изменения домена — это не требует ADR
  заранее, а фиксируется отдельным ADR в момент реального выделения
  (Milestone 10+).

## Альтернативы

- **Микросервисы с первого дня** — отклонено: преждевременная сложность,
  прямо запрещено требованиями, не даёт выгоды при одном владельце и
  умеренной нагрузке.
- **Serverless-функции** — отклонено: усложняет долгоживущие
  многоэтапные workflow и persistent browser-профиль владельца.

## Последствия

- Все инфраструктурные зависимости (Postgres-клиент, browser context,
  model SDK клиенты) инициализируются в рамках одного процесса на
  окружение (api/worker), что упрощает конфигурацию, но требует
  дисциплины при разделении ответственности между `apps/api` (приём
  запросов, чтение состояния) и `apps/worker` (исполнение миссий).
- Масштабирование по нагрузке в первой версии — вертикальное; горизонтальное
  масштабирование worker'ов и очередь заданий — предмет Milestone 10.
